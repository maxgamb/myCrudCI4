# myCrudCI4 Developer Architecture

This document is for developers who modify **myCrudCI4 itself**, not only applications generated by it.

## Core principle: generation-time over runtime discovery

If the database schema and persisted configuration identify a Model, Service, table, foreign key, pivot, or relation while code is being generated, emit explicit PHP for it. Do not postpone that decision to runtime.

```php
// Preferred: explicit generated dependency.
return (new LanguageService())->createRelated($payload);
return (new ActorModel())->relationRowsByIds($ids);

// Avoid: runtime discovery for a relation already known by the generator.
$service = new $serviceClass();
$model = new $modelClass();
$db->table($definition['table']);
```

This makes generated code readable, statically inspectable, testable, and easier to customize.

## Generator pipeline

```text
Database schema
    ↓
DbSchema / schema policies
    ↓
CrudConfigurationService / ConfigBuilder
    ↓
persistent app/MyCrudConfig/<table>.php
    ↓
CrudGeneratorService
    ↓
architecture + specialized generators
    ↓
app/Generated/
    ↓ review / diff / tests
app/ + tests/
```

The live database is authoritative for physical facts. Persistent configuration stores developer decisions and must not freeze obsolete schema facts.

## Generated application boundaries

```text
BASIC READ/WRITE
Controller → Model → Database

STANDARD/FULL WEB READ
Controller → Model → Database

STANDARD/FULL WEB WRITE
Controller → Service → Entity → Model → Database

REST READ
ApiController → Model → Resource → JSON

REST WRITE
ApiController → Service → Entity → Model → Database

MCP READ
MCP Tool → Model → MCP Resource

CROSS-RESOURCE WRITE
Service A → explicit Service B → Model B
```

### Controller
Owns HTTP request/response, view data, redirects and HTTP-level context. It must not compose SQL. In Standard/Full, application writes go through the Service.

### Service
Owns write use-cases, application validation/normalization, transactions, extension hooks and explicit cross-resource write orchestration. It must not compose SQL or call `Database::connect()`.

For Standard/Full persistence, the Service prepares and validates the payload, runs the pre-write hook, then creates the generated Entity with `Entity::fromArray()`. `fromArray()` is a construction boundary, **not a validation boundary**.

### Entity
Represents one application record. It owns CI4 casts/dates and may contain accessors, mutators, normalization or behavior intrinsic to that record. It must not query the database, open transactions or orchestrate other resources. Generated `DECIMAL`/`NUMERIC` fields are not forced to PHP `float`, preserving exact decimal values for domains such as money.

### Model
Owns queries and persistence. Concrete Models declare schema-known relational query methods explicitly.

### BaseCrudModel
Owns reusable infrastructure for the **current Model/table**: common list/persistence helpers, cache and transaction API. It must not become a relation registry or runtime resolver.

### REST/MCP Resource
Output serializer/projection only. It must not query, persist, validate writes or resolve dependencies. Input/filter/sort policy belongs to the boundary (ApiController or MCP Tool).

### ServiceExtension
Persistent application customization point outside `app/Generated/`. It is create-only and must never be overwritten by regeneration/publishing.

## Relational code

BelongsTo, HasMany and many-to-many behavior must remain feature-aware. Generate only the methods needed by the current table. A known relation should result in a named concrete method/dependency, not a metadata-driven runtime dispatcher.

## Generated vs persistent code

`app/Generated/` is disposable staging. Generator-owned operational files can be republished. Developer-owned persistent extension points and configuration must survive complete staging deletion.

During scaffolding, repeated generation with `--force` is expected. After published application code has been intentionally customized, destructive regeneration/publishing must be reviewed first. Git is the final safety net for application-level changes.

## Architecture changes

When changing an architectural boundary, update all of the following as applicable: generator, generated contract tests, CLI diagnostics, developer docs, AI context, REST/OpenAPI and MCP. A test should assert the architectural invariant rather than an accidental formatting detail.


## Dashboard read architecture

Dashboard is a read-only composition boundary. Aggregate/statistical queries belong to generated `DashboardQuery`. Record-shaped Recent widgets reuse concrete generated Models selected at generation-time. Their Entity/object/array results are normalized through Dashboard DTOs before the View boundary. Runtime Model-class discovery is not permitted when the Dashboard generator already knows the concrete Model.
